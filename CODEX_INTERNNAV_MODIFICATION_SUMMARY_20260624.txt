3) 独立红点跟踪原型 pixel_goal_nav/

设计原则：不修改 internnav/、原 g1_client/、原启动脚本或现有 5801/eval_dual 服务；独立使用 5802/eval_pixel_goal。

- server.py：复用模型的像素目标推理，忽略 latent trajectory 的直接控制用途；输出 pixel_goal_uv 与 base_link 下的 local_goal。
- geometry.py：先使用胸前居中、近似水平相机的简化投影；15x15 深度中值、无效深度拒绝、0.4--1.2m 目标截断；预留完整相机外参配置。
- g1_client.py：局部目标结合 odom 转世界坐标、20 点短路径和 MPC；默认 dry-run，必须 --enable-motion 才发布控制。
- calibrate_camera.py 与 configs/：为后续相机到机体外参标定预留独立配置。
- 每次请求/控制保存 RGB、深度、像素点、局部/世界目标、odom 与控制输出至 pixel_goal_nav/runs/。
- 已执行过独立服务器与 G1 端的部署/日志回收；真实运行发现同步 HTTP 和同步写图会造成中途顿挫。

4) 红点跟踪“平滑版”尝试

涉及：pixel_goal_nav/smooth_g1_client.py、smooth_scheduler.py、async_logging.py、run_smooth_g1_client.sh、tests/test_smooth_scheduler.py、README.md。

- 目标：用 ReentrantCallbackGroup + MultiThreadedExecutor、单 HTTP worker、10Hz 独立控制、深度去抖和异步日志，减少 HTTP 推理和写盘导致的停顿。
- 当前单测结果：geometry 5/5、smooth 28/28，共 33/33 通过。
- 但本轮代码审查未通过实机启用验收：
  a. 安全恢复检查、创建 MPC、accept_goal 不是一个原子状态转换；危险帧可能在中间到达又被 accept_goal 清除。
  b. AsyncRunLogger.close() 在 writer 仍存活时可能关闭 events 文件；已用临时复现确认 close 返回后 writer 仍可存活。
  c. 恢复门控仅拒绝首次进入 hold 前的目标，恢复安全帧期间的在途旧目标仍可能被接受。
- 结论：smooth_g1_client.py 目前不要带 --enable-motion 上实机；需先修复上述竞态和退出路径，并补覆盖生产客户端的集成测试。
